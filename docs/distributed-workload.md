# Distributed Workload

This document fixes the workload for the distributed benchmarks. The
one-worker baseline, multi-worker scaling, bottleneck profiling and
fault injection all run on this same workload instead of each defining
their own.

## Workload

```text
ml/src/ai_earth_intelligence_and_forecasting_engine/distributed/workload.py
```

```text
grid_version:    v1   (data.grid.GRID_VERSION)
dataset_version: v1   (forecast.build_dataset.DATASET_VERSION)
feature_version: v1   (forecast.build_dataset.FEATURE_VERSION)
model_version:   calibrated_xgboost_v1 (ml/artifacts/calibrated_xgboost_v1/)
workload_size:   500 tiles
tile_ids:        the first 500 tiles of the California grid,
                 in the grid's fixed lat/lon index order
                 (data.grid.build_california_grid()[:500])
```

The workload has 500 tiles, not the full grid of about 10,000. That is
large enough for parallel work to matter (on a handful of tiles,
speedup and efficiency would be noise), and small enough for a
one-worker baseline to finish in a reasonable time on a local machine,
without a cluster.

The tiles are the first 500 in grid order, not a random sample. Reusing
the existing fixed order (which its own tests show is stable) is the
simplest choice and needs no random seed. The requirement is a fixed
batch, not a representative one.

## Why the version identifiers are reused

`grid_version`, `dataset_version` and `feature_version` are the
constants already defined elsewhere (`data.grid.GRID_VERSION`,
`forecast.build_dataset.DATASET_VERSION` and `FEATURE_VERSION`), not new
strings for this workload. A workload record that named a dataset
version the rest of the project did not know would make results harder
to reproduce.

`model_version` (`calibrated_xgboost_v1`) is new, because no earlier
work named one. The earlier ablation and baseline runs each fitted
calibrated XGBoost in memory and never saved the trained model.
`ml/artifacts/calibrated_xgboost_v1/` holds only `config.json` and a
`README.md`: the settings and a description, not a saved model. The
one-worker baseline is the first benchmark that needs a fitted model to
run inference with many times. It fits one from the same config and
keeps it fixed for the whole benchmark run. Training is not part of
what the distributed work measures.

## Result

```text
ml/artifacts/distributed_workload_v1/workload.json
```

A record generated by `scripts/distributed/freeze_workload.py`: 500 tile
ids and the four version identifiers above. Like every entry under
`ml/artifacts/`, it is ignored by git and can be rebuilt.

## Out of scope

This document does not run a forecast, measure time or use a worker.
It only fixes what every distributed benchmark holds constant: the
tiles, the dataset and the model.
